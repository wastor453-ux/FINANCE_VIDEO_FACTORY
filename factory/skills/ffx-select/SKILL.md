# Select

- Command: `ffx select --in runs/_staging/discovery.json --seen state/seen_videos.json --out runs/_staging/selection.json`. `_staging/` because the run folder doesn't exist yet (its id is derived from the winner this stage picks); `state/seen_videos.json` lives outside any run folder on purpose -- it's cross-run memory that must survive archiving and retention cleanup, never per-video data.
- Logic (see lib/select.mjs): a channel can only win with its single latest long-form, non-live upload (owner's requirement, 2026-10-28) -- not any older long-form video, even one that scores higher, and not a short even if it's the channel's newest upload of any length. If a channel's most recent output is only shorts, that channel has no candidate this week; it is not skipped by substituting an older long-form video. Beyond that: not seen before, 24 h to 10 d old. Score = outlier vs the channel's own recent baseline (weight 0.6), engagement (0.25), absolute reach (0.15), all on a log scale. The baseline (which still looks at a channel's recent history of OTHER videos, including older ones, to judge whether the latest is unusual) is bounded by `baselineMaxAgeDays` so long-past uploads can't drag it down and make a normal new upload look like a false outlier (see the comment in `config/pipeline.json` -> `selection`). Small channels can therefore beat big ones on real signal, not on a stale comparison.
- Present to the user: winner, 3 runners-up, the metrics that explain the pick, and any caveats (hidden likes, fallback baselines, failed channels, channels with no eligible candidate this week).
- Why "already seen" is permanent, not folder-based: `state/seen_videos.json` is the single source of truth for "never cover this video again" and deliberately lives outside `runs/`/`archive/` so it is never touched by the 15-day retention cleanup -- if "already seen" were instead derived by reading old archived run folders, that memory would silently expire after 15 days and a video could get re-selected. Discovery itself is already cheap and incremental in effect: it only ever fetches each channel's most recent handful of uploads (not a full channel history), and `already_seen` then filters out anything already covered, so a channel that posted nothing new since last week naturally contributes no new eligible candidate -- no separate "diff against last week" logic is needed.
- G1: wait for approval or a manual pick. Once approved: run `node factory/bin/ffx.mjs run-init --channel <winner's handle> --video <winner's videoId> --title "<winner's title>"`, copy `runs/_staging/discovery.json` and `runs/_staging/selection.json` into the new `runs/<runId>/`, record the stages (`run-set-stage runs/<runId> discover VERIFIED`, `... select VERIFIED`), approve the gate (`run-approve runs/<runId> G1 --by owner --note "<winner>"`), then run `ffx mark-seen --selection runs/<runId>/selection.json --seen state/seen_videos.json`.
- Also check topic fit: skip a winner whose topic is breaking news that will be stale, or which needs claims we cannot source; offer the first runner-up instead.
